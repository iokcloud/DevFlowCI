## 决策 #001：采用结构化记忆文件 + 会话仪式作为项目协作基础

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：DevFlow CI 是一个长期演进的多 Agent 协作项目。传统方式下，每次新 AI 会话都需要人类重新描述上下文，效率低下，且经验无法跨会话传承。需要建立一套可跨 AI 实例接续的协作机制。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 无结构化协作（自由对话） | 零启动成本 | 每次重置上下文，经验无法积累，质量不稳定 |
  | B. 结构化记忆文件 + 会话仪式（本方案） | 上下文可恢复、经验可积累、质量可量化 | 需要维护文件体系的纪律 |
  | C. 外部知识库系统（Notion/Wiki） | 界面友好 | 增加外部依赖，AI 无法自动读写 |

- **选择**：方案 B — 使用项目文件系统中的 Markdown/JSON 文件作为记忆载体。这是 AI 可以直接读写的、无外部依赖的、版本可控的最小可行方案。
- **影响**：影响整个项目的协作方式。所有开发活动需遵循 AI_COLLABORATION_GUIDE.md 中定义的仪式。每次会话开始 AI 需读取记忆文件，结束需写入会话总结。
- **风险/代价**：需要维护记忆文件的纪律。如果懈怠，记忆会过时并产生误导。已将 "记忆库有效利用率" 纳入质量度量指标（目标 >60%）来追踪。

## 决策 #002：选择 Python 3.12 + FastAPI + LangGraph 作为核心栈

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：DevFlow CI 需要一个支持多 Agent 协作、异步工作流、RESTful API 的技术栈。Python 生态在 AI/LLM 领域最为成熟，FastAPI 提供高性能异步 API，LangGraph 提供 Agent 工作流编排。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | Python + FastAPI + LangGraph | AI 生态最成熟，异步原生支持，LangGraph 专门为 Agent 编排设计 | GIL 限制（可接受，IO 密集为主） |
  | TypeScript + Express + LangChain.js | 前后端统一语言 | AI/Agent 生态不如 Python 成熟 |
  | Python + Flask + 自建编排 | 简单灵活 | 需要自己实现工作流引擎，工作量大 |

- **选择**：Python 3.12 + FastAPI 0.115 + LangGraph 0.2.56 — 最大化利用现有 AI Agent 生态，减少重复造轮子。
- **影响**：所有后端代码使用 Python 3.12；API 层使用 FastAPI；Agent 编排使用 LangGraph。
- **风险/代价**：Python 生态包版本冲突是已知痛点，需要严格管理依赖版本。LangGraph 迭代快，API 可能变化。

## 决策 #003：使用 SQLite + aiosqlite + SQLAlchemy 作为数据层

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：DevFlow CI 需要持久化 Agent 状态、工作流执行记录和项目上下文。本地开发阶段不需要外部数据库服务。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | SQLite + SQLAlchemy（异步） | 零运维，本地单文件，ORM 支持好 | 并发写性能有限 |
  | PostgreSQL | 生产级并发 | 需要外部服务，本地开发不便 |
  | JSON 文件 | 最简单 | 无查询能力，数据一致性无保证 |

- **选择**：SQLite + aiosqlite + SQLAlchemy 2.0 — 本地开发零运维，后续可平滑迁移到 PostgreSQL。
- **影响**：数据库文件存储在 `database/` 目录下。
- **风险/代价**：SQLite 并发写瓶颈在 CI 多 Agent 同时操作时可能暴露。解决：后续可加 WAL 模式或迁移到 PostgreSQL。

## 决策 #004：取消简单/复杂分类，统一为项目开发模式

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：v0.1 将项目分为"简单需求"和"大型项目"，执行路径不同（简单需求一键执行，大型项目分阶段确认）。实践中发现，用户并不清楚自己的需求属于哪种类型，且分类型导致 PM Agent 的行为受到硬编码约束，不够灵活。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 保持简单/复杂分类 | 路由清晰 | 用户需判断类型，AI 粒度被约束 |
  | B. 统一项目模式（本方案） | 用户只需一个输入框，AI 自动判断粒度 | 所有项目走完整流程，简单需求可能"过度规划" |
  | C. 完全由用户指定模块数 | 精确控制 | 需要用户了解技术细节，增加使用门槛 |

- **选择**：方案 B — 取消 type 字段，所有项目统一走 规划→并行模块→集成→全局审查→交付 流程。PM Agent 根据需求复杂度自动判断拆解粒度（1-2 个模块到 10 个模块不等）。
- **影响**：前端移除类型切换控件；后端 CreateProjectRequest 移除 type 字段；PM Agent 移除 is_complex 参数，改为自动判断。
- **风险/代价**：简单需求可能被过度拆解为 3 个模块。缓解：PM Agent 的 system prompt 明确要求"简单需求 1-2 模块，中等需求 2-4 模块"。

## 决策 #006：永不卡死的工作流策略

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：v0.1 中，单个模块审查失败 3 次后整个项目失败，用户体验差。需要一个更弹性的策略，即使部分模块未完成也能交付可用成果。
- **选择**：
  1. 模块审查重试 3→5 次
  2. 5 次后仍失败 → blocked（而非 failed），生成骨架占位文件
  3. 集成阶段将 blocked 模块的占位文件放入正确位置
  4. 生成 TODO.md 记录未完成模块及其修复建议
  5. 全局审查检查 blocked 模块导致的接口断裂
  6. 非模块阶段（规划/集成/全局审查）异常最多重试 3 次，仍失败 → needs_review
  7. 只要规划、集成、全局审查完成，项目状态即为 completed
- **影响**：workflow/executor.py、langgraph_def.py 的路由逻辑、models.py 的 ModuleStatus（新增 BLOCKED）和 ProjectStatus（新增 NEEDS_REVIEW）。
- **风险/代价**：blocked 模块的占位文件可能产生错误期望。缓解：占位文件顶部包含详细注释，TODO.md 明确说明每个模块的阻塞原因。

## 决策 #007：项目级记忆独立维护

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：对于同一个项目目录的多次操作，需要有跨会话的记忆，记录规划历史、模块状态和修改轨迹。这与通用的成功案例库（success_cases.json）功能不同，后者是基于 TF-IDF 的跨项目相似性检索。
- **选择**：
  1. 新增 memory/project_memory/ 目录，以目录路径的 MD5 哈希命名 JSON 文件
  2. 每次交付后更新该文件：记录最近规划、模块列表及状态、最近修改模块
  3. 新操作开始时（上下文分析后），若记忆文件存在则注入 PM Agent
  4. 项目记忆与成功案例库独立维护，不互相污染
- **影响**：memory/project_memory.py、agents/planner.py（接收 project_memory_text 参数）、workflow/executor.py（更新记忆）。
- **风险/代价**：如果项目目录路径变化（移动/重命名），哈希不同会导致记忆丢失。缓解：记忆文件中有 directory 字段记录原始路径，后续可做模糊匹配。

## 决策 #008：引入异常自愈机制

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：v0.2 的"永不卡死"策略保证了系统不会因为部分模块失败而完全停止，但模块失败后的处理是消极的（直接生成占位文件，等待人工介入）。用户期望系统能主动尝试修复常见问题，减少人工干预。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 直接阻塞（当前方案） | 简单可靠 | 人工干预频率高，效率低 |
  | B. 固定重试 | 不增加复杂度 | 对非临时性错误无效 |
  | C. 结构化错误分类 + 多重修复策略 + 案例进化（本方案） | 覆盖多种错误类型，策略渐进增强，经验可积累 | 增加系统复杂度，依赖 LLM 修复质量 |

- **选择**：方案 C — 实现完整的异常自愈流水线：
  1. **错误分类**：基于关键词模式匹配，将错误分为 API_TIMEOUT、SYNTAX_ERROR、TEST_FAILURE、REVIEW_FAIL、DEPENDENCY_MISSING、UNKNOWN 六类。
  2. **多重策略回退**：直接重试（指数退避）→ 编码Agent修改代码 → RepairAgent反思修复 → 历史案例参考修复 → 阻塞。
  3. **修复案例库**：每次修复成功记录到 `memory/auto_fix_cases.json`，使用 Jaccard 相似度检索历史案例注入 RepairAgent。
  4. **安全护栏**：总修复轮次上限 8 次，修复后必须经审查Agent验证（最多 2 次快速审查），所有修复动作记录日志。
  5. **前端联动**：修复中显示旋转图标，修复成功显示绿色卡片。
- **影响**：
  - 新增 `agents/repair_agent.py` — 反思修复 Agent
  - 新增 `workflow/auto_fix.py` — 错误分类、案例检索、策略调度
  - 新增 `memory/auto_fix_cases.json` — 修复案例存储
  - 更新 `config.py` — ErrorType 枚举、自愈配置参数
  - 更新 `workflow/executor.py` — `_execute_single_module` 集成自愈流程
  - 更新 `database/models.py` — 新增 `AUTO_FIXING` 状态和 `auto_fix_history` 字段
  - 更新前端 — 修复状态显示和修复历史详情
- **风险/代价**：
  - LLM 修复质量不确定：可能引入新的 bug。缓解：修复后强制审查（最多 2 次快速审查）。
  - 案例库冷启动：初期无历史案例可参考。缓解：RepairAgent 自身推理能力足够处理常见错误。
  - LLM 调用成本：每次修复试图都会调用 LLM。缓解：8 轮硬上限，且策略按成本递增顺序排列。
  - 与永不卡死策略的衔接：自愈是阻塞前的"最后努力"，无论成功与否系统都会继续运行。

## 决策 #009：引入三层自动化测试与质量验证

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：v0.2 具备"永不卡死"和"异常自愈"，但模块代码的实际运行正确性完全依赖 LLM 的静态审查判断。用户反馈指出：LLM 审查无法替代实际执行——只有真正运行测试才能发现运行时错误、逻辑 bug 和依赖问题。需要在工作流中嵌入真实的测试执行，实现端到端的质量闭环。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 仅 LLM 审查（当前） | 零额外开销 | 无法发现运行时问题 |
  | B. 仅语法检查 | 快速安全 | 不检查逻辑正确性 |
  | C. 三层测试执行（本方案） | 真实验证，多级保障 | 增加时间开销，依赖运行环境 |

- **选择**：方案 C — 模块级（pytest 执行）→ 集成级（跨模块验证）→ 交付级（全量测试报告）三层测试体系。
  - **模块级**：LLM 生成测试代码后，在隔离沙箱中用 subprocess 运行 pytest，失败则触发自愈流程。
  - **集成级**：集成 Agent 生成集成测试后运行，结果传给全局审查 Agent。
  - **交付级**：打包前运行所有测试，生成 `test_report.json`。≤2 个失败→completed_with_warnings，>2 个失败→附带报告提示人工检查。
  - **降级方案**：pytest 不可用时自动降级为 `compile()` 语法检查。
  - **安全**：所有测试在 `temp` 沙箱中执行，超时硬限制（30s/60s/120s），异常不导致主流程崩溃。
- **影响**：新增 `workflow/test_runner.py`；更新 `config.py`（TEST_EXECUTION_FAILURE + 超时配置）；更新 `executor.py`（三级测试集成）；数据库新增 `test_result`/`test_report_path` 字段；前端新增测试徽章、质量摘要弹窗、日志过滤器。
- **风险/代价**：依赖 pytest 和 subprocess 权限——Windows/受限环境可能不可用，降级方案保证不中断流程。沙箱中的 import 依赖可能不完整——由模块代码自包含度决定。

## 决策 #010：多方案生成 — 用户从操作者变为决策者

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：v0.2 的 PM Agent 只输出单一规划方案，用户只能"接受"或"手动修改"。实际开发中，不同的架构选择（分层 vs 领域驱动、微服务 vs 单体）会极大影响项目质量，用户希望在规划阶段就能参与决策而非被动接受。
- **选择**：PM Agent 新增 `plan_alternatives()` 方法，生成方案A/方案B对比（含结构化优劣势分析），前端展示对比卡片。用户 120 秒内可选择方案，超时自动选方案A。
- **影响**：`agents/planner.py` 新增 `ALTERNATIVE_PLAN_PROMPT` + `plan_alternatives()`；前段新增方案对比面板。

## 决策 #011：依赖智能推断与门禁

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：编码 Agent 可能引入未声明的依赖（如 import 了某个库但 requirements.txt 没写），导致交付物不可运行。需要一个前置的依赖检查机制。
- **选择**：上下文分析后、PM 规划前加入依赖推断节点，LLM 分析需求输出 `dependencies.yaml` 草案；编码 Agent 以该清单为编码边界；测试执行失败时自动对照清单检查缺失依赖。
- **影响**：`planner.py` 新增 `DEPENDENCY_INFERENCE_PROMPT` + `infer_dependencies()`；`executor.py` 在 `plan_only` 中调用依赖推断；前端展示依赖清单表格。

## 决策 #012：版本化交付 — 自动化代码生成的安全网

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：每次运行 CI 都可能覆盖上一次的交付物，一旦新版本有回归问题，用户无法快速恢复。版本化交付是任何自动化代码生成系统不可或缺的安全网。
- **选择**：交付目录改为 `deliveries/{pid}/v1/`, `/v2/` ...；保留最近 5 个版本，更旧的自动归档为 ZIP；新增 `POST /rollback` API 可回滚到任意版本；前端展示版本树。
- **影响**：`executor.py` 的 `_package_delivery` 支持版本化；`main.py` 新增 `/versions` 和 `/rollback` API；前端版本树面板。

## 决策 #013：反馈学习 — 个人化 AI 助手的终极养料

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：所有 LLM 生成的代码都有"通用性"特征——按照训练数据中的常见模式编写。但每个用户/团队有自己独特的编码风格、安全偏好和架构习惯。如果不学习这些偏好，系统永远是"通用助手"而非"个人专属伙伴"。
- **选择**：通过 `POST /feedback` API 记录每次人工修改（原始代码→修改后代码→修改类型）；存储到 `memory/human_fixes.json`；下次 PM Agent 和编码 Agent 工作时注入"人类偏好参考"文本；每积累 20 条自动生成偏好学习报告（偏好报告 API: `GET /preferences`）。
- **影响**：`memory/human_fixes.json` 存储人工修改对；`planner.py` 的 `load_human_preferences()` 加载并格式化偏好；`main.py` 新增 `/feedback` 和 `/preferences` API。

## 决策 #014：自治项目孵化 — 预埋运维能力使项目自营

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：CI 助手的价值不应在代码生成时结束。成熟系统应让每个生成的项目天然内置自我运维、自我修复和自我进化的骨架，使项目能独立运行和持续优化。

## 决策 #015：增加需求对齐阶段 — 防止方向错误，低成本纠偏

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：当前工作流在用户提交需求后直接进入 PM 规划，中间缺少一个"需求理解确认"环节。如果 AI 对需求的理解有偏差，整个后续规划、编码、测试流程都会跑偏，纠偏成本极高。需要一个低成本的前置对齐点，让用户在开发启动前确认 AI 的理解是否正确。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 直接进入规划（当前） | 流程简单 | 方向错误后纠偏成本高 |
  | B. 需求对齐前置（本方案） | 低成本纠偏，提升信任 | 增加一步用户交互 |
  | C. 多次对话澄清 | 理解深入 | 耗时太长，用户不耐受 |

- **选择**：方案 B — 在所有构建工作流启动前强制执行需求对齐阶段。
  1. 新增 `AlignmentAgent`（需求分析师），融合用户需求、项目文档和项目记忆，输出结构化对齐 JSON（摘要、假设、风险、建议模块、待澄清问题）。
  2. 在 LangGraph 图中，原"PM 规划"节点之前插入 `requirement_alignment` 节点。
  3. 状态流转：`created` → `aligning` → `aligned` → 用户确认 → `planning` → ...
  4. 对齐结果前端展示为模块卡片确认页，用户可勾选/编辑，确认后写入 `DELIVERY_PLAN.md`。
  5. 超时不自动执行，保持在 aligned 状态，防止错误开工。
  6. 对齐产生的假设和风险记录到 decisions.md。
- **影响**：
  - 新增 `agents/alignment_agent.py`
  - 更新 `database/models.py`（新增 ALIGNING/ALIGNED 状态、alignment_json 字段）
  - 更新 `workflow/langgraph_def.py`（新增 requirement_alignment 节点）
  - 更新 `workflow/executor.py`（新增 execute_alignment 方法，拆分 execute）
  - 更新 `main.py`（API 状态映射、confirm_plan 支持 aligned）
  - 更新前端（对齐过渡动画、确认页、模块编辑）
  - 更新 `config.py`（对齐超时配置）
- **风险/代价**：
  - 增加一步用户交互，简单需求可能感觉流程过长。缓解：对齐分析速度通常在 5-15 秒内完成。
  - AlignmentAgent 基于 LLM，分析质量取决于 prompt 设计。缓解：结构化输出格式约束 + 验证逻辑确保输出完整性。
  - 如果目录为空且无文档，AlignmentAgent 仅基于需求生成计划，可能缺少技术上下文。缓解：assumptions 字段明确列出基于需求的假设，供用户审查。

## 决策 #016：商业文档模式路由 — 基于本地化关键词库 + 兜底策略

- **日期**：2026-05-31
- **状态**：已采纳
- **上下文**：当前系统支持商业智能模式（BusinessPlannerAgent），可在用户提交市场调研/行业分析等商业文档时生成商业计划建议书。但实践中发现，`_detect_document_type()` 的关键词库仅包含约 25 个偏重商业分析的词汇，无法覆盖"交易数据""课件""教案""话题热度""问卷调研"等常见中文商业文档类型。导致商业文档被误判为 `generic`，AlignmentAgent 返回 `insufficient_info`。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 仅扩展关键词库 | 简单直接 | 关键词库永远无法穷举，新增文档类型仍需人工补充 |
  | B. 扩展关键词库 + 兜底策略（本方案） | 覆盖主要场景 + 无法识别时仍能合理路由 | 兜底策略依赖二次确认逻辑，增加少量复杂度 |
  | C. 用 LLM 做文档分类 | 零维护成本、覆盖面广 | 增加 LLM 调用延迟和成本；在上下文分析阶段 LLM 已被用于生成文档摘要，再调用一次会显著增加延迟 |

- **选择**：方案 B — 扩展中文商业关键词库（新增 80+ 词汇，按交易/消费/市场/用户画像/营销/教育/话题/融资/渠道分类）+ 双重兜底策略：
  1. `_detect_document_type()` 层：当 `b_count >= 1` 且 `t_count == 0`（至少 1 个商业关键词且 0 个技术关键词）→ 返回 `business`。
  2. `execute_alignment()` 层：当 `doc_type == "generic"` 但文档中没有任何技术关键词 → 强制切换为 `business`。
  3. 增加 `document_type` 判定日志输出，便于问题调试。
  4. 统一接口命名：`BusinessPlannerAgent.plan()` 作为主入口，`generate()` 为底层实现。
- **影响**：
  - 修改 `workflow/executor.py`：`_detect_document_type()` 关键词库扩展 + 判定逻辑调整；`execute_alignment()` 兜底策略 + 日志
  - 修改 `agents/business_planner.py`：新增 `plan()` 方法
  - 不影响下游模块（plan/execute/integrate），仅影响对齐阶段的路由选择
- **风险/代价**：
  - 关键词库扩展可能导致部分边缘 case 被误判为商业文档（如文档同时包含商业和技术内容）。缓解：技术关键词权重高于商业关键词，`technical` 判定需要 `t_count >= 3`，优先级最高。
  - 关键词库仍需持续维护。缓解：在 LEARNINGS.md 中记录维护策略。

## 决策 #017：流式传输显示与错误日志智能管理

- **日期**：2026-06-01
- **状态**：已采纳
- **上下文**：当前系统通过 SSE 日志流和轮询提供项目状态更新，但缺少两个关键能力：1) AI 实时 thinking 过程的可视化（用户只能等结果，不知道 AI 在"想什么"）；2) 全局错误日志的聚合分析和自动清理能力（错误散落在各模块日志中，缺乏系统级视图和自动修复闭环）。
- **方案对比**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A. 不做，依赖现有日志 | 零开发成本 | AI 过程不透明，错误无法聚合分析 |
  | B. 仅前端轮询模拟流式 | 简单 | 不真实，浪费带宽 |
  | C. DeepSeek stream=True + SSE 推送 + ErrorLog 表 + 维护 API（本方案） | 真实流式体验、错误可聚合分析、自动修复闭环 | 增加后端复杂度，需处理流式降级 |

- **选择**：方案 C —
  1. **流式 AI 输出**：启用 DeepSeek API `stream=True`，通过 `asyncio.Queue` 桥接 SSE 推送到前端，支持暂停/继续、不同 Agent 颜色标签。超时或异常时优雅降级为非流式调用，不阻塞主工作流。
  2. **ErrorLog 数据库表**：新增 `error_logs` 表（trace_id, project_id, module_name, error_type, message, stacktrace, status），所有 ERROR/WARN 级别日志双写（文件 + 数据库）。
  3. **维护 API**：`POST /api/maintenance/analyze-errors` 聚合 open 错误并调用 RepairAgent 批量修复；`POST /api/maintenance/clean-logs` 自动清理 7 天前已解决的错误；`GET /api/maintenance/error-stats` 提供统计视图。
  4. **前端联动**：新增"实时 AI 输出"面板和"错误统计"面板，在项目启动时自动加载。
  5. **案例库联动**：`analyze-errors` 修复成功时自动将模式提取到 `auto_fix_cases.json`。
- **影响**：
  - 新增 `workflow/stream_relay.py` — 流式调用 + SSE 推送
  - 新增 `workflow/error_logger.py` — 错误写库/统计/清理
  - 更新 `database/models.py` — 新增 `ErrorLog` 表 + `ErrorStatus` 枚举
  - 更新 `main.py` — 新增 4 个 API 端点 + 导入
  - 更新 `workflow/executor.py` — `push_log()` 同步写 ErrorLog
  - 更新 `static/index.html` — 新增面板 HTML
  - 更新 `static/app.js` — `connectAiStream()`, `loadErrorStats()` 等函数
  - 更新 `static/style.css` — 流式面板和错误统计样式
- **风险/代价**：
  - 流式调用依赖 httpx 和 SSE，如果 DeepSeek API 不支持 SSE 流式响应，自动降级为分块推送模式。
  - ErrorLog 表写入采用 try/except 包裹，失败不阻塞主流程。
  - `install_requires` 需包含 `httpx`（用于流式 HTTP 请求）。
