### 教训 #001：结构化错误分类 + 历史修复案例库是 Agent 自愈的两大支柱

- **日期**：2026-05-31
- **来源**：异常自愈机制设计与实现
- **类别**：设计缺陷
- **现象**：在引入自愈机制前，模块审查失败多轮后只能立即阻塞，等待人工介入。用户需要手动分析错误日志、修改代码、重新运行，效率低。
- **原因**：系统缺乏对错误的"理解"能力——无法区分暂时性错误（API超时）和结构性错误（语法/逻辑），也无法从过往的修复经验中学习。
- **解决方案**：
  1. **结构化错误分类**：基于关键词模式匹配将错误分为 6 大类（API_TIMEOUT、API_RATE_LIMIT、SYNTAX_ERROR、TEST_FAILURE、REVIEW_FAIL、DEPENDENCY_MISSING），每类映射不同的修复策略优先级。
  2. **历史修复案例库**：每次修复成功自动记录到 `auto_fix_cases.json`，使用 Jaccard 相似度检索相似案例，注入 RepairAgent 作为参考——实现"进化自愈"。
- **预防措施**：
  - 新增错误类型时，在 `_ERROR_PATTERNS` 中添加关键词映射
  - 每个修复策略都应有独立的日志标识（如 `[自愈·策略名]`），便于前端和人工追踪
  - 修复案例库需定期审查，确保案例质量（避免"坏经验"被复用）
- **Prompt 改进**：否（自愈机制不依赖 Prompt 模板变更）

### 教训 #002：E2E 测试脚本必须有心跳、足够超时和 UTF-8 兼容，否则会误判为「卡死」

- **日期**：2026-06-01
- **来源**：test_flow.py 端到端验证
- **类别**：协作流程
- **现象**：运行 `python test_flow.py` 时终端长时间无输出，用户以为进程卡死；实际 LLM 工作流需 3–10 分钟。Windows PowerShell 还可能因 GBK 编码在打印 emoji 时直接崩溃。
- **根因**：
  1. 旧版测试只在状态变更时打印，executing 阶段可沉默数分钟
  2. 默认或环境遗留的超时过短（如 180s）
  3. 模块进度未增量写入 DB，API 一直显示 `模块=0`
  4. 工作流异常后状态未回写，项目永久停在 `planning`
- **解决方案**：
  1. test_flow.py 增加 15s 心跳、900s 默认超时、UTF-8 输出
  2. executor 增量持久化 plan/modules；push_log 的 state_event 同步 DB
  3. main.py 异常时写入 needs_review，不再静默吞掉
  4. 提供 `scripts/test_flow.bat` 统一 Windows 启动方式
- **预防措施**：所有长时间 E2E 脚本必须有心跳；文档注明 LLM 阶段预期耗时；修改 backend 后重启 uvicorn。
- **Prompt 改进**：否

### 教训 #003：多方案生成让用户从操作者变为决策者，提升信任

- **日期**：2026-05-31
- **来源**：四层增强 — 智能规划
- **类别**：设计缺陷
- **现象**：早期版本 PM Agent 只输出单一方案，用户只能接受或手动修改全部模块分解。这导致用户对系统的规划能力持怀疑态度，尤其在大型项目中不敢完全信任 AI 的架构决策。
- **原因**：单一方案剥夺了用户的选择权——不同的架构思路（分层/领域驱动/事件驱动）各有优劣，用户的领域知识应参与这一决策。
- **解决方案**：PM Agent 同时生成方案A和方案B，附带结构化优劣势对比。前端展示对比卡片，用户选择后继续执行（120s 超时自动选A）。
- **预防措施**：方案对比应包含明确的 trade-off 说明，避免让用户在两个同等模糊的方案间选择。
- **Prompt 改进**：是 — 新增 `ALTERNATIVE_PLAN_PROMPT`

### 教训 #004：版本化交付是任何自动化代码生成系统不可或缺的安全网

- **日期**：2026-05-31
- **来源**：四层增强 — 版本化交付
- **类别**：设计缺陷
- **现象**：v0.2 的交付物每次覆盖上一次结果，一旦新生成的代码有回归问题，用户无法快速恢复到之前的良好状态。这降低了用户对自动化的信任，阻碍高频使用。
- **原因**：自动化代码生成天然具有不确定性（LLM 输出变化），没有版本化就没有快速恢复能力。
- **解决方案**：版本化目录（v1/v2/...）、保留最近5个活跃版本、旧版本自动归档ZIP、POST /rollback API、前端版本树UI。
- **预防措施**：版本号应在项目数据库记录中保留版本链，便于审计。
- **Prompt 改进**：否

### 教训 #005：人工修改反馈是个人化 AI 助手的终极养料

- **日期**：2026-05-31
- **来源**：四层增强 — 反馈学习闭环
- **类别**：设计缺陷
- **现象**：LLM 生成的代码遵循训练数据中的"平均风格"，但每个团队和用户有自己的编码习惯（如"我们总是用 pydantic 做输入校验"、"我们偏好函数式风格"）。没有反馈机制，系统永远是通用工具而非个人伙伴。
- **原因**：缺乏持续学习的闭环——用户的每次手动修改都是一条珍贵的训练信号，但没有渠道收集和利用。
- **解决方案**：
  1. `POST /feedback` API 收集每次人工修改（原始→修改后→修改类型）
  2. 存储到 `human_fixes.json`
  3. 下次 Agent 工作时注入"人类偏好参考"文本
  4. 每 20 条累积生成偏好学习报告
- **预防措施**：反馈记录应匿名化敏感信息（代码片段截取有限长度）。偏好学习报告需人类确认后才固化为 Prompt 的永久优化。
- **Prompt 改进**：是 — `load_human_preferences()` 动态注入

### 教训 #006：实际测试执行是 LLM 审查不可替代的质量保障

- **日期**：2026-05-31
- **来源**：三层自动化测试系统设计
- **类别**：设计缺陷
- **现象**：在引入实际测试执行前，系统仅依赖 LLM 审查判断代码质量。LLM 可能给出"PASS"的审查结论，但代码在运行时仍可能因 import 错误、类型不匹配、逻辑 bug 等原因崩溃。
- **原因**：LLM 审查是静态的、基于模式的评估，无法替代真实的代码执行和测试运行。只有通过 subprocess 运行 pytest 才能真正验证代码的正确性。
- **解决方案**：实现三层测试执行体系：
  1. **模块级**：每个模块的测试代码在隔离沙箱中运行 pytest，失败即触发自愈
  2. **集成级**：集成测试运行结果反馈给全局审查 Agent
  3. **交付级**：打包前运行全量测试，生成 `test_report.json`，根据失败数量决定交付策略
  4. **降级保障**：pytest 不可用时自动降级为 `compile()` 语法检查，保证不中断流程
- **预防措施**：
  - 所有测试执行必须在临时沙箱中进行，超时硬限制
  - 新增 `TEST_EXECUTION_FAILURE` 错误类型纳入自愈体系
  - 前端实时展示测试徽章和质量摘要，让用户第一时间了解质量状态
- **Prompt 改进**：否

### 教训 #007：在生成阶段预埋运维能力是使项目自营的最经济方式

- **日期**：2026-05-31
- **来源**：自治项目孵化
- **类别**：设计缺陷
- **现象**：CI 生成的代码缺少监控端点、自我诊断能力和自动修复机制。项目部署后用户必须手动运维，遇到错误时只能回到 CI 重新生成或手动修复。
- **原因**：代码生成的目标仅定义为"功能正确"，忽略了"可持续运行"的运维维度。等项目部署后再逐一添加这些能力，成本远高于在生成阶段预埋。
- **解决方案**：设计 5 个可复用的自治运维组件模板；集成阶段自动注入到每个生成项目；根据项目类型适配主入口；所有组件通过环境变量控制开关。
- **预防措施**：新自治组件优先以"模板 + 注入"方式提供，而非要求各项目自行实现。
- **Prompt 改进**：是 — integrator 的 README 生成提示词更新

### 教训 #008：需求对齐是自治开发中不可或缺的人类确认点

- **日期**：2026-05-31
- **来源**：需求对齐阶段设计与实现
- **类别**：设计缺陷
- **现象**：在引入需求对齐阶段前，系统在用户提交需求后直接进入 PM 规划和代码生成。当 AI 对需求理解有偏差时（如将"用户认证"理解为简单的用户名密码而非 OAuth），整个后续流程跑偏，纠偏成本极高——需要重新规划、重新编码、重新审查。
- **原因**：全自动化的流程缺少前置的"理解确认"环节。AI 对自然语言的理解天然存在歧义空间，缺少人类在关键节点的确认会导致错误被放大。
- **解决方案**：
  1. 在所有构建工作流启动前强制执行需求对齐阶段。
  2. AlignmentAgent 融合用户需求、项目文档和项目记忆，输出结构化分析结果（摘要、假设、风险、建议模块、待澄清问题）。
  3. 前端展示确认页，用户可勾选模块、编辑描述、补充问题，确认后进入规划。
  4. 超时不自动执行——这与规划阶段的自动确认策略不同，对齐阶段是"安全优先"：宁可等人工确认，也不错误开工。
- **预防措施**：
  - 任何新增的 AI 自主决策环节前，评估是否需要人类确认点
  - 确认点的设计应遵循"低成本、高价值"原则：交互简单但对方向正确性有高影响
  - 超时策略根据确认点的重要性区分：方向性确认（如需求对齐）不应自动跳过，优化性确认（如方案选择）可设超时默认值
- **Prompt 改进**：是 — 新增 `ALIGNMENT_SYSTEM_PROMPT` 和 `MULTI_PLAN_PROMPT`

### 教训 #009：需求对齐必须严格基于实际文档内容，泛化建议会摧毁用户信任

- **日期**：2026-05-31
- **来源**：需求对齐精准化修复
- **类别**：设计缺陷
- **现象**：用户选择已有项目目录但不输入需求时，AlignmentAgent 给出"分层重构、加强日志测试"等通用建议，完全无视目录中实际文档（README.md、API 文档等）内容。用户立刻丧失信任——"AI 根本没看我的项目，就在胡说八道"。
- **原因**：
  1. 上下文分析节点只输出纯文本碎片，没有结构化摘要，AlignmentAgent 无法有效利用。
  2. AlignmentAgent 的 Prompt 允许"通用最佳实践建议"，缺少"必须基于文档"的硬约束。
  3. 没有交叉验证机制——生成计划后不检查模块是否与文档内容有关联。
- **解决方案**：
  1. **上下文分析增强**：新增 `analyze_project_context_structured()`，递归收集 .md/.txt/.rst 文档，调用 LLM 生成 per-file 摘要和 overall_summary，输出结构化 JSON。
  2. **Prompt 重写**：三大约束——① 只能基于文档摘要生成计划；② 禁止"改善代码质量"等通用建议；③ 信息不足直接返回 `insufficient_info`。
  3. **自检机制**：`_self_check_plan()` 用关键词匹配检查每个模块是否能在文档摘要中找到依据，找不到的标记 `flagged: true`。
  4. **前端联动**：insufficient_info → 显示友好提示 + 需求输入框重新提交；flagged 模块 → 虚线边框 + ⚠️ 警告；evidence 字段 → 📎 依据图标悬停查看来源。
- **预防措施**：
  - 任何"基于上下文生成建议"的 Agent，必须实现内容溯源机制
  - 上下文分析输出必须是结构化 JSON（analyzed_files + summaries），而不是自由文本
  - 新增 `no_documentation_found` 标志位，让下游 Agent 明确知道何时应该返回 insufficient_info
- **Prompt 改进**：是 — ALIGNMENT_SYSTEM_PROMPT 完全重写

### 教训 #010：中文商业文档识别需使用本地化关键词库，且需在技术上确保路由正确执行

- **日期**：2026-05-31
- **来源**：商业智能模式失效 Bug 修复
- **类别**：设计缺陷
- **现象**：用户提交包含"教育课件交易数据分析""热门话题分析报告"等中文商业文档的项目目录，系统始终输出 `insufficient_info`（"文档不足以生成技术执行计划"），未能识别为商业文档并切换到 BusinessPlannerAgent。
- **原因**：
  1. `_detect_document_type()` 的商业关键词库仅 25 个词，缺少"交易数据""课件""教案""话题""热度""问卷""调研"等常见中文商业词汇，导致 `b_count` 始终 < 3。
  2. 即使识别为 `generic`，也没有兜底策略：当文档中技术关键词为 0 时，应默认尝试商业模式。
  3. `execute_alignment()` 中没有记录 `document_type` 的实际判定值，导致问题难以调试。
  4. `BusinessPlannerAgent` 缺少 `plan()` 方法作为主入口，路由调用与接口不一致。
- **解决方案**：
  1. **扩展关键词库**：新增 80+ 中文商业关键词，按类别组织（交易/消费/市场/用户画像/营销/教育/话题/融资/渠道等）。
  2. **兜底策略**：`_detect_document_type()` 中新增规则 — 当 `b_count >= 1` 且 `t_count == 0` 时返回 `business`；在 `execute_alignment()` 中二次确认 — 若 `doc_type == "generic"` 但文档内容中无任何技术关键词，强制切换为 `business`。
  3. **调试可见性**：在 `execute_alignment()` 中添加 `await push_log(pid, "INFO", f"文档类型判定: {doc_type}")` 日志。
  4. **接口统一**：为 `BusinessPlannerAgent` 添加 `plan()` 方法作为主入口（内部委托给 `generate()`）。
- **预防措施**：
  - 商业关键词库应与业务需求同步增长，每次遇到新的商业文档类型都应补充关键词
  - 所有"模式切换"逻辑必须有可见日志，便于追溯判定过程
  - Agent 接口应使用一致的命名规范（`plan()` 作为主入口方法），`generate()` 作为底层实现
- **Prompt 改进**：否 — 底层 LLM Prompt 无需改动，本修复为纯逻辑层改进

### 教训 #011：流式 AI 输出 + 错误日志双写是 Agent 系统可观测性的两大支柱

- **日期**：2026-06-01
- **来源**：流式传输显示与错误日志智能管理功能实现
- **类别**：设计缺陷
- **现象**：在引入流式输出前，用户提交需求后只能看加载动画等待 AI 响应，完全不知道 AI 在"想什么"。错误日志散落在 SSE 流和日志文件中，无法聚合分析；人工排查错误需要翻几十条日志。
- **原因**：系统缺少两个关键能力：
  1. **AI 思维过程可视化**：LLM 调用是同步的，用户只能等完整响应返回。
  2. **错误日志结构化存储**：错误只在 SSE 流中推送，没有持久化到数据库，无法聚合查询和批量修复。
- **解决方案**：
  1. **流式 AI 输出**：启用 DeepSeek `stream=True` + httpx SSE → asyncio.Queue → SSE 端点 `/stream-ai` → 前端 EventSource。前端区分不同 Agent 的颜色标签，支持暂停/继续自动滚屏。流式失败时优雅降级为分块推送。
  2. **ErrorLog 数据库表**：新增 `error_logs` 表，`push_log()` 中 ERROR/WARN 级别双写文件 + 数据库。
  3. **维护 API**：`POST /api/maintenance/analyze-errors` 聚合 open 错误 → LLM 分析模式 → RepairAgent 批量修复 → resolved；`POST /api/maintenance/clean-logs` 清理旧记录。
  4. **案例库联动**：自动修复成功后提取模式写入 `auto_fix_cases.json`。
- **预防措施**：
  - 所有 LLM 调用应考虑流式支持，无法流式时提供降级方案
  - 错误日志统一使用结构化表存储，避免仅依赖文本文件
  - 维护 API 应提供 dry_run 模式，允许安全预览清理效果
- **Prompt 改进**：否 — 本次改进为基础设施层，不涉及 Agent Prompt

### 教训 #012：纯商业 MVP 应聚焦 Phase-1 单模块，而非 PM 多模块拆分

- **日期**：2026-06-01
- **来源**：商业 E2E 3/3 blocked（run 26755443769）与 nightly smoke 对比
- **类别**：设计缺陷
- **现象**：商业确认后技术规划拆成 3 个抽象模块，审查全部 FAIL → blocked，工作流仍 `completed` 但交付为 stub。
- **原因**：
  1. `_build_business_tech_requirement` 对非 is_prime 需求仅拼接摘要 + `cap=3`，PM 仍倾向多模块拆分。
  2. Reviewer 对 MVP 代码使用与完整产品相同的严格标准，轻微问题即 FAIL。
- **解决方案**：
  1. 商业确认后取 roadmap 第一阶段首项 action 生成**单模块**技术需求（`mvp_max_modules=1`）。
  2. Reviewer 在 `mvp_mode=True` 时附加放宽指引；Executor 在 cap=1 时自动启用。
  3. Weekly E2E 用 `TEST_FLOW_BUSINESS_MODE=full` 验证纯商业路径（无 is_prime 短路径）。
- **预防措施**：
  - 商业 → 技术衔接应显式指定「Phase-1 单模块」而非仅模块数上限
  - E2E 质量断言（`test_flow_quality`）与 blocked 分析脚本并用
- **Prompt 改进**：是 — Reviewer 增加 `REVIEWER_MVP_ADDON`；规划侧已有 MVP cap prompt

### 教训 #000：示例 — 异步 SQLite 连接未在应用关闭时释放

- **日期**：2026-05-31
- **来源**：本地测试时发现
- **类别**：Bug — 代码错误
- **现象**：`uvicorn` 关闭后进程不退出，日志显示 `sqlite3.ProgrammingError: Cannot operate on a closed database`
- **原因**：`aiosqlite` 连接在 `lifespan` 事件中创建，但 `shutdown` 阶段未调用 `await db.close()`
- **解决方案**：在 FastAPI `lifespan` 的 `yield` 之后显式关闭连接池
- **预防措施**：
  - 数据库连接的 `lifespan` 生命周期管理加入代码审查清单
  - 在 `AGENT_PROMPT_TEMPLATES.md` 的编码者模板中增加 "数据库连接释放" 检查项
- **Prompt 改进**：是 — 关联 AGENT_PROMPT_TEMPLATES.md 编码者模板 §资源管理

### 教训 #014：增量规划勿把「已通过模块」仅写在 dependencies 里

- **日期**：2026-06-03
- **来源**：AiEDU 迭代 — `web_app` / `polish_api` 规划验证失败（`llm_client`、`prompt_service` 不在本次 plan）
- **类别**：设计缺陷
- **现象**：PM 将项目记忆里已 `passed` 的模块写入新 plan 的 `dependencies`，但 `modules` 未包含它们，`validate_plan` 报「依赖不存在」，重试 3 次仍失败。
- **原因**：
  1. 校验只认当前 `modules` 列表，未考虑 `project_memory` 中已交付模块。
  2. Prompt 虽要求依赖必须在 plan 内，LLM 在增量场景仍常引用历史模块名。
- **解决方案**：
  1. `ProjectMemoryStore.get_passed_module_names()` + `validate_plan(..., external_modules=)` 认可已通过模块。
  2. `sanitize_plan_dependencies()` 修剪既不在 plan、也不在 passed 集合的无效依赖。
  3. `format_for_prompt()` / `PLANNER_SYSTEM_PROMPT` 明确：已通过模块勿列入 `modules` 与 `dependencies`，在 `description` 写「复用已有 xxx」。
- **预防措施**：
  - 迭代前确认目标目录的 `memory/project_memory/<hash>.json` 中 passed 列表与预期一致。
  - 新增规划校验单测时覆盖 `external_modules` 场景（见 `test_planner_validate.py`）。
- **Prompt 改进**：是 — `agents/planner.py` 规则 8/10、`memory/project_memory.py` 已通过模块说明

### 教训 #015：本地 ruff 版本须与 CI（requirements-dev.txt）一致

- **日期**：2026-06-03
- **来源**：GitHub Actions run #49 失败 — 本地 `ruff check` 全绿但 CI 16s 内 exit 1
- **类别**：协作流程
- **现象**：`19d2d0a` 提交后 Actions 仍红；Annotations 仅「exit code 1」，实为 **Lint (ruff)** 步骤失败。
- **原因**：
  1. CI 安装 `ruff==0.11.0`（`requirements-dev.txt`），开发者全局/venv 可能是 0.15+，规则集与自动修复不一致。
  2. pre-commit 长期只跑 pytest，未跑 `ruff check .`，提交前无法发现 CI 专有问题。
- **解决方案**：
  1. 用 **venv** 执行与 CI 相同版本：`venv\Scripts\python.exe -m pip install ruff==0.11.0` 后 `ruff check .`。
  2. 修复 0.11 下剩余项（如 `db.py` I001、`UP038` 等）并推送 `7469f66`。
  3. pre-commit 增加 `ruff check .`；Actions 升级 `checkout@v6` / `setup-python@v6` 消除 Node 20 弃用警告。
- **预防措施**：
  - 提交前习惯：`pip install -r requirements-dev.txt` 后用 **同一解释器** 跑 `ruff check .` 与 `pytest`。
  - 若升级 ruff 版本，须同时改 `requirements-dev.txt` 并在 PR 说明规则差异。
- **Prompt 改进**：否 — 见 `docs/DEVELOPMENT.md`、`.github/workflows/ci.yml`
